## 2. Comment on issue #543 (RX 9070 XT: builder runs, 86 GB/frame refresh)

```markdown
A reading of why the refresh grows that large, from `crates/victory-gpu/src/memory.rs` at `c96b4f2`. It's a
hypothesis from the code only; we have no RDNA 4 run of our own yet.

`memory::ready()` runs for every dispatch that reaches title memory by address. For each numbered copy (up to
1,023, mostly 4 MiB windows) it calls `shadow.refresh(...)` when `list.first_use(READ)` is true, i.e. at the first
such dispatch **in each host list**, and `shadow.gpu_writes(...)` at the first such write in each list. The module's
own `shortcut:` note says the same ("Every dispatch of such a shader brings all numbered copies up to date and, if it
can store, declares all of them written... a dirty-page mask written by the shader would bound both").

With your 962 copies that's up to ~3.8 GB per list. Since `c96b4f2`'s default of 256 lists in flight, the builder's
dispatches are spread over many lists. About 22 lists a frame with builder dispatches would give your ~87 GB. And
every builder write marks the pages changed, so each list's refresh really copies them again.

Two cheap things you could try on your card, if you have time:
1. `VICTORY_INPLACE=1` with the builder on: title memory is opened as a graphics heap, and an in-place copy makes
   `refresh` and `gpu_writes` do nothing (`Shadow::placed` in `shadow.rs`). It's experimental and, as far as I can
   tell, untested on AMD.
2. Fewer lists per frame for the builder's work (`VICTORY_LATE_WAIT_LISTS` lower than the default), to see whether
   refresh MB/frame drops in proportion. That would confirm or rule out the per-list explanation.

If neither helps, the fix the code itself suggests is a dirty-page mask written by the translated shader on each
store by address, so only touched pages are copied back and invalidated. I've started on that and will link it when
it builds and has tests.
```

## 3. Comment on issue #505 (RX 9070: driver shader compiler crash)

```markdown
In case it helps: #422 ties a crash at this same `amdxc64.dll+0x861b9f` offset to the translator's clean-up pass 4
(REUSE). `VICTORY_SHADER_OPT=59` (every pass except 4) clears it on an RX 9070 XT at `c96b4f2`, as reported in #543.
The shader cache is keyed by that setting, so the programs are translated afresh. Two programs (`c1eee35dbc50a9ef`,

to find and skip pipelines the driver's compiler crashes on.
```

## 4. Comment on PR #414 (BVH: absent child sorted before a real hit)

```markdown
A data point on what this should match. Mesa's RADV driver (the open-source Vulkan driver for AMD GPUs) has a
software emulation of this box test. It uses it on hardware without the instruction: `intersect_ray_amd_software_box`
in `src/amd/vulkan/nir/radv_nir_rt_common.c` (Mesa `e175081`, 2026-11-24). Per child it checks:

    /* if (!isnan(node->coords[i][0].x) && tmax >= max(0.0f, tmin) && tmin < ray_tmax) { */

and on a hit stores `child_indices[i] = node->children[i]` without testing the pointer. So a child with pointer
`0xFFFFFFFF` whose bounds pass the slab test does get a finite distance there, and an absent child is switched off
only by a NaN minimum x. That's what `bvh::boxes` does today.

It's an emulation, not the hardware, so it doesn't settle what the console's GPU does. But it suggests the current
behaviour matches what an AMD driver team chose, and that absent children are expected to carry NaN bounds. Unless
there's evidence the console's instruction checks the pointer, I'd keep the current behaviour.
```

## 5. Comment on PR #464 (BVH: reject partial-axis NaN and inverted boxes)

```markdown
For comparison, Mesa RADV's software emulation of the same box test (`intersect_ray_amd_software_box`,
`src/amd/vulkan/nir/radv_nir_rt_common.c`, Mesa `e175081`) checks NaN only on the minimum x:

    /* If x of the aabb min is NaN, then this is an inactive aabb.
     * We don't need to care about any other components being NaN as that is UB. */

It has no min <= max test. Per axis it takes `fmin`/`fmax` of the two slab distances, so an inverted box acts as the
box with its corners swapped rather than being rejected. The fork's `bvh::boxes` matches that today. RADV's comment
calls NaN in the other components UB, so that case can't be settled from there. But rejecting inverted boxes would
make the fork behave differently from AMD's open-source driver. That emulation isn't the console hardware either, but
without evidence of what the console does, matching it seems the safer default.
```
